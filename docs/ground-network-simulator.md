# Ground Network Simulator

Cadence includes an external provider simulator for contact-scheduling development,
constellation demonstrations, and end-to-end telemetry testing without commercial
ground-network access.

The simulator is deliberately split across two boundaries:

- the provider HTTP API models opportunity discovery, reservation, cancellation,
  lifecycle status, and provider events;
- the existing TCP provider adapter carries CCSDS telemetry only while a contact is
  active.

Cadence owns scheduling intent, canonical scheduled/realized contacts, framing,
ingress, and telemetry persistence. The simulator owns synthetic visibility,
provider capacity, external lifecycle behavior, and generated bytes.

> **Current implementation:** The simulator contract and normalized Cadence
> Provider Client use the accepted
> [Simulator Provider Contract v1](superpowers/specs/2026-07-13-simulator-provider-contract-v1.md)
> through separate `/admin/v1` and `/provider/v1` surfaces. Tasks 1-8 of the
> [Stage 2 implementation plan](superpowers/plans/2026-07-13-contact-scheduling-stage-2-provider-delivery-contract.md)
> are complete. Cadence now persists Mission Providers and provider-managed
> Transports with exact Service and Delivery Profile versions. Scheduling and
> reservations persist exact Routing Rule, Transport, Mission Provider, and
> profile bindings before provider mutation. The internal Provider Profile is
> now execution evidence only.

## Start the services

The simulator and Cadence are started independently. From the simulator app:

```bash
export CADENCE_SIMULATOR_HTTP_ENABLED=true
export CADENCE_SIMULATOR_PORT=4101
export CADENCE_SIMULATOR_ADMIN_API_TOKEN=local-simulator-admin-token
export CADENCE_SIMULATOR_PROVIDER_API_TOKEN=local-simulator-provider-token
export CADENCE_SIMULATOR_STORE_PATH="$PWD/var/cadence_simulator_provider.dets"
export CADENCE_SIMULATOR_DEFINITIONS_PATH="$PWD/legacy/cadence_legacy/priv/databases/demo_spacecraft.yaml"

cd apps/cadence_simulator
mix run --no-halt
```

Start Cadence separately, then configure the mission through **Comms → Providers**.
Cadence does not start, stop, or administer simulator scenarios. The simulator
exposes its own API for scenario and run administration.

The simulator has its own configuration tree and production dependency graph.
It does not load Cadence's database or Phoenix runtime configuration.

## Integration flow

1. Start the simulator and create a scenario/run through its admin API.
2. Start Cadence.
3. Configure the Mission Provider in **Comms → Providers**, validate access, and
   synchronize its inventory and profiles. Provision a TCP Delivery Profile
   through the provider API when the desired profile does not exist yet.
4. Create a **Ground Station Provider** Transport in **Comms → Transports** and
   select the synchronized Service and Delivery Profiles. Cadence derives the
   TCP runtime setup as read-only configuration.
5. Map Cadence spacecraft/source endpoints to the provider spacecraft IDs.
6. Open **Ops → Contacts**, search the provider, and reserve an opportunity.
7. During an active contact, the simulator connects to the advertised Cadence
   telemetry endpoint and streams CCSDS frames.

This is the same control-plane/data-plane split expected of a commercial ground
station provider.

## Provider API

All endpoints use JSON. `/admin/v1` uses the simulator administrator credential;
`/provider/v1` uses the provider credential plus an
`X-Simulator-Environment-Ref` header. Contact creation accepts an
`Idempotency-Key` header only when capabilities declare native idempotency.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/admin/v1/scenarios` | Persist a reusable fleet/station/fault definition |
| `POST` | `/admin/v1/scenarios/:id/runs` | Start an immutable provider environment |
| `POST` | `/admin/v1/runs/:id/pause` | Pause lifecycle advancement |
| `POST` | `/admin/v1/runs/:id/resume` | Resume lifecycle advancement |
| `POST` | `/admin/v1/runs/:id/stop` | Stop a run |
| `GET` | `/provider/v1/account` | Validate access to the selected environment |
| `GET` | `/provider/v1/capabilities` | Discover behavior and supported operations |
| `GET` | `/provider/v1/spacecraft` | List the modeled fleet |
| `GET` | `/provider/v1/ground-stations` | List simulated sites and antenna capacity |
| `GET` | `/provider/v1/service-profiles` | List provider services |
| `GET/POST` | `/provider/v1/delivery-profiles` | List or provision delivery destinations |
| `POST` | `/provider/v1/opportunities/search` | Generate deterministic synthetic windows |
| `POST` | `/provider/v1/contacts` | Reserve an opportunity using profile references |
| `GET` | `/provider/v1/contacts?client_reference=...` | Recover a Contact by client correlation reference |
| `GET` | `/provider/v1/contacts/:id` | Read Contact, pass, and delivery state |
| `POST` | `/provider/v1/contacts/:id/cancel` | Cancel provider capacity |
| `GET` | `/provider/v1/events?cursor=...` | Consume the versioned provider event feed |

Contact lifecycle is:

```text
pending -> confirmed -> active -> completed
```

Terminal alternatives are `rejected`, `canceled`, and `failed`. Pass phase and
delivery status remain independent lifecycle dimensions.

## Scenario model

The default scenario models 500 spacecraft and three ten-antenna stations.
Visibility is synthetic and explicitly marked as such. Windows are repeatable from
the run seed, spacecraft identity, pass cadence, duration, and bounded jitter.
Changing the run speed compresses future pass cadence and duration into wall time.

Fault profiles support:

- scheduling rejection and complete provider outage;
- acquisition failure and early termination;
- packet loss applied before the network send buffer;
- network latency and deterministic jitter.

Scenario and run definitions, reservations, and events are stored in DETS and
survive restart. High-rate telemetry remains exclusively in Cadence.

## Cadence provider configuration

Open **Comms → Providers → New Provider** and configure:

- display name and provider type `Ground Network Simulator`;
- provider API base URL, such as `http://127.0.0.1:4101`;
- an opaque credential reference, such as
  `config://ground-network-simulator` or `env://CADENCE_SIMULATOR_PROVIDER_API_TOKEN`;
- the provider environment reference returned by the simulator admin API.

For a `config://ground-network-simulator` reference, configure the runtime
secret outside the provider record:

```elixir
config :cadence, :ground_network_credentials, %{
  "ground-network-simulator" => System.fetch_env!("CADENCE_SIMULATOR_PROVIDER_API_TOKEN")
}
```

Use **Validate** to check account and environment access, then **Sync Inventory**
to cache bounded provider inventory, Service Profiles, and Delivery Profiles.
Provider inventory never creates Cadence spacecraft automatically. Secrets are
not persisted in Mission Provider setup or provider evidence.

The older Provider Profile remains an internal runtime compatibility resource.
It is no longer provider control-plane identity or a product object shown under
**Comms → Providers**.

`Cadence.Contacts.ProviderBooking` persists a first-class
`ProviderReservation`, including its idempotency key and preallocated Scheduled
Contact ID, before requesting provider capacity. The provider call occurs
outside the database transaction. Confirmed capacity materializes the Scheduled
Contact idempotently; pending or ambiguous outcomes remain durable for the
supervised status reconciler to resolve after process restart. Contact
realization continues through the existing contact scheduler and TCP provider
runtime.

Scheduling readiness is derived from the mission's product comms graph:

- the mission spacecraft mapping supplies the provider spacecraft reference;
- an enabled inbound Routing Rule selects the exact runtime path and Transport
  version;
- a provider-managed Transport selects the exact Mission Provider, Service
  Profile, and ready compatible Delivery Profile versions;
- the materialized Provider Profile is retained only as exact runtime execution
  evidence;
- direct Transports remain valid for local scheduling but never gain external
  opportunity search from their runtime materialization.

The authenticated operator workflow lives at
`/missions/:mission_id/ops/contacts`. It shows Provider, Service, Delivery,
Transport, Contact status, pass phase, and delivery status separately and
supports search, reservation, durable convergence, and cancellation. Exact
references and sanitized descriptor state remain available in administrator
diagnostics.

Telemetry definitions remain simulator-owned. The TCP destination and framing
are provisioned once as a Delivery Profile. Contact requests contain only
opportunity, spacecraft, service, delivery, client-correlation, and tag
references; they do not carry endpoint fields or generator settings.

## Shared CCSDS library

`cadence` and `cadence_simulator` both depend on the leaf application
`cadence_ccsds`. The shared app owns the `Cadence.CCSDS.*` codecs, segmentation,
reassembly, and COP-1 primitives. The simulator has no production dependency on
Cadence core; Cadence is present only in the simulator test environment for
end-to-end integration coverage.
