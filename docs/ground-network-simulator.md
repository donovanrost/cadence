# Ground Network Simulator

Cadence includes an external provider simulator for contact-scheduling development,
constellation demonstrations, and end-to-end telemetry testing without commercial
ground-network access.

The simulator is deliberately split across two boundaries:

- the provider HTTP API models opportunity discovery, reservation, cancellation,
  lifecycle status, and provider events;
- the existing TCP provider adapter carries CCSDS telemetry only while a contact is
  active.

Cadence owns scheduling intent, canonical scheduled/realized contacts, framing,
ingress, and telemetry persistence. The simulator owns synthetic visibility,
provider capacity, external lifecycle behavior, and generated bytes.

> **Current implementation:** The simulator contract and normalized Cadence
> Provider Client use the accepted
> [Simulator Provider Contract v1](superpowers/specs/2026-07-13-simulator-provider-contract-v1.md)
> through separate `/admin/v1` and `/provider/v1` surfaces. Stage 4 of the
> [requirements and planning plan](superpowers/plans/2026-07-16-contact-scheduling-stage-4-requirements-and-planning.md)
> builds on the completed Stage 3
> [durable integration plan](superpowers/plans/2026-07-15-contact-scheduling-stage-3-durable-integration-semantics.md)
> and is implemented. Organization-owned Provider Accounts own endpoint,
> environment, credential reference, guardrails, and provider-event ingestion.
> Exact mission grants authorize Mission Providers, which own mission mappings
> and delivery policy. Reservations preserve requested, provider-confirmed, and
> Cadence-accepted truth plus exact account, grant, Provider, Transport,
> Service Profile, and Delivery Profile versions. Provider events, changes,
> approvals, acknowledgments, audit evidence, and Scheduled Contact revisions
> are durable across restart. Mission-owned Contact Requirements, immutable
> provider search evidence, versioned Contact Plans, named approval evidence,
> and restart-safe Plan execution now use that same provider boundary.

## Start the services

The simulator and Cadence are started independently. From the simulator app:

```bash
export CADENCE_SIMULATOR_HTTP_ENABLED=true
export CADENCE_SIMULATOR_PORT=4101
export CADENCE_SIMULATOR_ADMIN_API_TOKEN=local-simulator-admin-token
export CADENCE_SIMULATOR_PROVIDER_API_TOKEN=local-simulator-provider-token
export CADENCE_SIMULATOR_STORE_PATH="$PWD/var/cadence_simulator_provider.dets"
export CADENCE_SIMULATOR_DEFINITIONS_PATH="$PWD/legacy/cadence_legacy/priv/databases/demo_spacecraft.yaml"

cd apps/cadence_simulator
mix run --no-halt
```

`CADENCE_SIMULATOR_HTTP_ENABLED` defaults to `false`; the HTTP provider peer is
not started unless it is enabled. `CADENCE_SIMULATOR_PORT` defaults to `4101`.
The DETS path defaults to `var/cadence_simulator_provider.dets`, and the
definitions path has no default. Set distinct administrator and provider tokens
for the normal development flow. When a token is configured, its namespace
requires that bearer token.

Start Cadence separately. An organization administrator registers the simulator
under **Provider Accounts** and grants it to a mission; a mission administrator
then enables the granted account under **Comms → Providers**. Cadence does not
start, stop, or administer simulator scenarios. The simulator exposes its own
API for scenario and run administration.

The simulator has its own configuration tree and production dependency graph.
It does not load Cadence's database or Phoenix runtime configuration.

## Integration flow

1. Start the simulator and create a scenario/run through its admin API.
2. Start Cadence.
3. As an organization administrator, open **Provider Accounts**, register the
   simulator endpoint, run environment, and credential backend, validate it,
   and grant the exact account version to the mission.
4. In **Comms → Providers**, select that grant, narrow its resources if needed,
   configure the mission delivery policy, validate access, and synchronize
   inventory and profiles. Provision a TCP Delivery Profile through the provider
   API when the desired profile does not exist yet.
5. Create a **Ground Station Provider** Transport in **Comms → Transports** and
   select the synchronized Service and Delivery Profiles. Cadence derives the
   TCP runtime setup as read-only configuration.
6. Map Cadence spacecraft/source endpoints to the provider spacecraft IDs.
7. Open **Ops → Requirements**, describe the mission need, search all eligible
   provider routes, select an opportunity, and create a Contact Plan.
8. Submit the exact Plan version, approve it as an organization administrator,
   and execute it. **Ops → Contacts** remains available for direct ad hoc
   reservation without a Requirement or Plan.
9. During an active contact, the simulator connects to the advertised Cadence
   telemetry endpoint and streams CCSDS frames.

This is the same control-plane/data-plane split expected of a commercial ground
station provider.

## Provider API

All endpoints use JSON. `/admin/v1` uses the simulator administrator credential;
`/provider/v1` uses the provider credential plus an
`X-Simulator-Environment-Ref` header. Contact creation accepts an
`Idempotency-Key` header only when capabilities declare native idempotency.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/admin/v1/scenarios` | Persist a reusable fleet/station/fault definition |
| `GET` | `/admin/v1/scenarios` | List scenarios |
| `GET` | `/admin/v1/scenarios/:id` | Read one scenario |
| `POST` | `/admin/v1/scenarios/:id/runs` | Start an immutable provider environment |
| `GET` | `/admin/v1/runs` | List runs |
| `GET` | `/admin/v1/runs/:id` | Read one run and its `provider_environment_ref` |
| `POST` | `/admin/v1/runs/:id/pause` | Pause lifecycle advancement |
| `POST` | `/admin/v1/runs/:id/resume` | Resume lifecycle advancement |
| `POST` | `/admin/v1/runs/:id/stop` | Stop a run |
| `PATCH` | `/admin/v1/runs/:id/fault-profile` | Change bounded run-scoped provider and event faults |
| `POST` | `/admin/v1/runs/:id/contacts/:contact_id/changes` | Initiate a provider-side Contact change |
| `GET` | `/provider/v1/account` | Validate access to the selected environment |
| `GET` | `/provider/v1/capabilities` | Discover behavior and supported operations |
| `GET` | `/provider/v1/spacecraft` | List the modeled fleet |
| `GET` | `/provider/v1/ground-stations` | List simulated sites and antenna capacity |
| `GET` | `/provider/v1/service-profiles` | List provider services |
| `GET/POST` | `/provider/v1/delivery-profiles` | List or provision delivery destinations |
| `GET` | `/provider/v1/delivery-profiles/:id` | Read a Delivery Profile |
| `POST` | `/provider/v1/opportunities/search` | Generate deterministic synthetic windows |
| `POST` | `/provider/v1/contacts` | Reserve an opportunity using profile references |
| `GET` | `/provider/v1/contacts?client_reference=...` | Recover a Contact by client correlation reference |
| `GET` | `/provider/v1/contacts/:id` | Read Contact, pass, and delivery state |
| `PATCH` | `/provider/v1/contacts/:id` | Request a capability-declared timing or resource modification |
| `GET` | `/provider/v1/contacts/:id/result` | Read the terminal delivery result when ready |
| `POST` | `/provider/v1/contacts/:id/cancel` | Cancel provider capacity |
| `GET` | `/provider/v1/events?cursor=...` | Consume the versioned provider event feed |

Contact lifecycle is:

```text
pending -> confirmed -> active -> completed
```

Terminal alternatives are `rejected`, `canceled`, and `failed`. Pass phase and
delivery status remain independent lifecycle dimensions.

## Scenario model

The default scenario models 500 spacecraft and three ten-antenna stations.
Visibility is synthetic and explicitly marked as such. Windows are repeatable from
the run seed, spacecraft identity, pass cadence, duration, and bounded jitter.
Changing the run speed compresses future pass cadence and duration into wall time.

The simulator also owns synthetic orbit readiness. A scenario may set
`orbit_readiness.status` to `current`, `missing`, `expired`, or `processing`,
and may provide an `ephemeris_ref`, `version`, and bounded `validity_seconds`.
A current search page returns provider-level readiness in
`meta.provider_evidence.orbit_readiness` and repeats it on each opportunity as
bounded extension evidence. A non-current state returns the structured
`orbit_not_ready` provider error. Cadence records this evidence and never reads
the scenario or performs orbit propagation.

Stage 5 fleet scenarios may also define `route_profiles`. Each route profile
binds one ground station and Service Profile to an
`antenna_or_service_pool_ref`. Reusing that resource reference across synthetic
windows models provider-owned exclusive service-pool capacity. A profile can
add bounded `request_latency_ms`, a deterministic
`rate_limit_response_count` with `retry_after_seconds`, and an
`opportunity_expiry_offset_seconds`. These are simulator administration inputs;
Cadence sees only ordinary inventory, 429 provider errors, opportunities,
capacity conflicts, and bounded diagnostic evidence.

`CadenceSimulator.Provider.FleetScenarios.stage_five/1` provides the
qualification scenario: at least 300 spacecraft, three stations, shared
exclusive pools, route latency/rate limiting, asynchronous client-reference
recovery, current provider-owned orbit evidence, deterministic partial
reservation rejection, ambiguous Contact commit, and durable event-delivery
faults.

Fault profiles support:

- scheduling rejection and complete provider outage;
- acquisition failure and early termination;
- bounded Contact-create and Contact-modification responses lost after provider
  commit;
- event omission, duplication, delay, reordering, and identity collision;
- packet loss applied before the network send buffer;
- network latency and deterministic jitter.

Set `fault_profile.contact_response_loss_after_commit_count` to exercise an
ambiguous HTTP outcome. Provider behavior separately declares `native`,
`client_reference`, or `none` idempotency and whether client-reference recovery
is supported. Cadence follows those declared capabilities rather than assuming
that every provider accepts an idempotency header.

Scenario and run definitions, reservations, and events are stored in DETS and
survive restart. High-rate telemetry remains exclusively in Cadence.

## Cadence provider configuration

Endpoint, environment, and credential ownership is organization-scoped:

1. Open **Provider Accounts → Register Account** as an organization
   administrator.
2. Select `Ground Network Simulator`; set the base URL, region, the run's
   `provider_environment_ref`, and polling event mode.
3. Select a secret backend and enter only its locator. For local development,
   choose **Local environment** and use
   `CADENCE_SIMULATOR_PROVIDER_API_TOKEN`. `config/dev.exs` enables this local
   backend; unset or disable `:provider_local_credentials` outside local
   environments. For production, choose **External secret manager** and
   configure `config :cadence, :secrets` with `:secret_manager_url` (HTTPS by
   default) plus `:secret_manager_token` or `:secret_manager_token_env`.
4. Define organization guardrails, validate the account, and grant an exact
   account version to the mission. Grant restrictions may only narrow account
   services, directions, stations, delivery kinds, and quota.

Cadence persists a stable credential registry reference and backend key, never
secret material. Rotation updates the credential registry version behind the
same reference and does not recreate Mission Providers or Transports. Revoking
the credential or mission grant blocks new provider operations while preserving
reservations, contacts, and evidence for review.

Next open **Comms → Providers → New Provider**. Select the exact grant, configure
spacecraft/resource mappings and a mission delivery policy, then validate and
sync bounded inventory, Service Profiles, and Delivery Profiles. The default
policy requires approval for every material change. Bounded automatic policy
can accept only explicitly configured timing/duration and station tolerances in
the current form, and can never widen the Provider Account or grant.
Mission Provider forms deliberately have no base URL, environment, or credential
fields. Provider inventory never creates Cadence spacecraft automatically.

The older Provider Profile remains an internal runtime compatibility resource.
It is no longer provider control-plane identity or a product object shown under
**Comms → Providers**.

`Cadence.Contacts.ProviderBooking` persists a first-class
`ProviderReservation`, including its idempotency key and preallocated Scheduled
Contact ID, before requesting provider capacity. The provider call occurs
outside the database transaction. Confirmed capacity materializes the Scheduled
Contact idempotently; pending or ambiguous outcomes remain durable for the
supervised status reconciler to resolve after process restart. Contact
realization continues through the existing contact scheduler and TCP provider
runtime.

Scheduling readiness is derived from the mission's product comms graph:

- the mission spacecraft mapping supplies the provider spacecraft reference;
- an enabled inbound Routing Rule selects the exact runtime path and Transport
  version;
- a provider-managed Transport selects the exact Mission Provider, Service
  Profile, and ready compatible Delivery Profile versions;
- the materialized Provider Profile is retained only as exact runtime execution
  evidence;
- direct Transports remain valid for local scheduling but never gain external
  opportunity search from their runtime materialization.

Provider orbit readiness is a second, external prerequisite. Cadence sends a
bounded search horizon and provider spacecraft reference. The provider owns the
ephemeris, station geometry, propagation, and visibility result. Cadence stores
the returned ephemeris reference/version/validity as evidence, distinguishes
`not_ready` from successful empty availability, and reasons only over the
provider-authoritative windows.

The planning workflow lives at
`/missions/:mission_id/ops/requirements`, and exact Plan manifests live under
`/missions/:mission_id/ops/plans/:contact_plan_id`. The direct/ad hoc workflow
lives at `/missions/:mission_id/ops/contacts`. Each Contact row links to a durable detail
at `/missions/:mission_id/ops/contacts/:provider_reservation_id`. The detail
separates requested, provider-confirmed, Cadence-accepted, and actual truth;
shows provider, pass, delivery, and Cadence lifecycle independently; and exposes
the exact policy and configuration bindings used for every decision.

Provider and Transport setup routes live in the authenticated mission `:comms`
LiveView session. Contact scheduling lives in the authenticated mission `:ops`
session because it is an operational workflow, not durable setup. Both sessions
load organization and mission scope before rendering.

Telemetry definitions remain simulator-owned. The TCP destination and framing
are provisioned once as a Delivery Profile. Contact requests contain only
opportunity, spacecraft, service, delivery, client-correlation, and tag
references; they do not carry endpoint fields or generator settings.

## Event ingestion, changes, and recovery

One bounded Cadence worker lane polls active Provider Accounts. A database lease
protects each exact account/environment/channel cursor. Every page is normalized,
sanitized, bounded, integrity-hashed, and inserted into the durable inbox in the
same transaction that advances the opaque cursor. Duplicate deliveries converge;
same-ID/different-payload collisions, unknown event types, and poison events are
quarantined. Advisory events trigger an authoritative Contact describe; the
ordinary reservation reconciler remains the missing-event repair path.

After restart, polling resumes from the persisted cursor. An expired worker
lease is reclaimable automatically. On **Provider Accounts → Account detail**,
administrators can inspect cursor health, backlog, quarantine count, last-event
time, credential/grant status, and bounded audit activity. Correct the account,
credential, provider payload, or adapter first; an organization-authorized
recovery can then call
`Cadence.GroundNetworks.ProviderEventInbox.reprocess(current_scope, inbox_id)`.
Reprocessing is itself audited and converges through provider revision and
change identity rather than replaying an already-committed decision.

Provider revisions are evaluated against the exact snapshotted mission delivery
policy. In **Ops → Contacts → Contact detail**:

- bounded policy matches are accepted automatically and append one Scheduled
  Contact revision;
- future material proposals require a current organization-admin approval or
  rejection with reason;
- already-effective provider facts require acknowledgment and contingency work,
  because rejecting them cannot undo provider reality;
- endpoint, framing, credential, spacecraft, direction, Service Profile, or
  Delivery Profile drift is a non-approvable configuration failure.

The change timeline, approval/acknowledgment, provider event decision,
Scheduled Contact revision, credential version, and reconciliation outcome all
produce append-only, secret-free audit evidence. Provider protocol and endpoint
details remain inside the admin diagnostic disclosure rather than the ordinary
operator summary.

## Shared CCSDS library

`cadence` and `cadence_simulator` both depend on the leaf application
`cadence_ccsds`. The shared app owns the `Cadence.CCSDS.*` codecs, segmentation,
reassembly, and COP-1 primitives. The simulator has no production dependency on
Cadence core; Cadence is present only in the simulator test environment for
end-to-end integration coverage.

The focused scale test proves 500 modeled spacecraft with 25 concurrent active
TCP telemetry generators, contact-only worker allocation, and complete teardown at
contact end:

```bash
cd apps/cadence_simulator
mix test test/cadence_simulator/provider_scale_test.exs
```

The separate-app boundary tests start a real simulator HTTP listener, create an
organization Provider Account and exact mission grant, creates a Requirement,
persists orbit readiness and opportunities, approves and executes an exact Plan,
converges its execution item through provider reconciliation, processes events
and provider changes, rotates credentials, recovers ambiguous mutations,
realizes the ordinary Cadence contact, and verifies decoded telemetry received
through the configured TCP provider:

```bash
cd apps/cadence_simulator
mix test test/cadence_simulator/contact_scheduling_integration_test.exs
```

The scale suite additionally proves a real 300-spacecraft Fleet Planning Run
over provider HTTP with bounded concurrency and an ordinary candidate Plan. The
provider-only qualification proves successful empty availability, missing,
expired, and processing orbit states, shared-pool overlap, deterministic
rejection, capacity conflict, rate limiting, ambiguous response recovery, and
event replay after the simulator store process restarts.
