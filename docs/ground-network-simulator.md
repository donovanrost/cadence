# Ground Network Simulator

Cadence includes an external provider simulator for contact-scheduling development,
constellation demonstrations, and end-to-end telemetry testing without commercial
ground-network access.

The simulator is deliberately split across two boundaries:

- the provider HTTP API models opportunity discovery, reservation, cancellation,
  lifecycle status, and provider events;
- the existing TCP provider adapter carries CCSDS telemetry only while a contact is
  active.

Cadence owns scheduling intent, canonical scheduled/realized contacts, framing,
ingress, and telemetry persistence. The simulator owns synthetic visibility,
provider capacity, external lifecycle behavior, and generated bytes.

## Start the services

The simulator and Cadence are started independently. From the simulator app:

```bash
export CADENCE_SIMULATOR_HTTP_ENABLED=true
export CADENCE_SIMULATOR_PORT=4101
export CADENCE_SIMULATOR_API_TOKEN=local-simulator-token
export CADENCE_SIMULATOR_STORE_PATH="$PWD/var/cadence_simulator_provider.dets"
export CADENCE_SIMULATOR_DEFINITIONS_PATH="$PWD/legacy/cadence_legacy/priv/databases/demo_spacecraft.yaml"

cd apps/cadence_simulator
mix run --no-halt
```

Start Cadence separately, then configure the mission through the normal Comms
provider setup. Cadence does not start, stop, or administer simulator scenarios.
The simulator exposes its own API for scenario and run administration.

The simulator has its own configuration tree and production dependency graph.
It does not load Cadence's database or Phoenix runtime configuration.

## Integration flow

1. Start the simulator and create a scenario/run through its provider API.
2. Start Cadence.
3. Create a mission provider with TCP downlink delivery and the simulator
   scheduling integration.
4. Map Cadence spacecraft/source endpoints to the provider spacecraft IDs.
5. Search and reserve contacts through Cadence's provider boundary.
6. During an active contact, the simulator connects to the advertised Cadence
   telemetry endpoint and streams CCSDS frames.

This is the same control-plane/data-plane split expected of a commercial ground
station provider.

## Provider API

All endpoints use JSON. When `CADENCE_SIMULATOR_API_TOKEN` is set, send it as a
Bearer token. Reservation creation also accepts an `Idempotency-Key` header.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1/scenarios` | Persist a reusable fleet/station/fault definition |
| `GET` | `/v1/scenarios/:id` | Read a scenario |
| `POST` | `/v1/scenarios/:id/runs` | Start an immutable scenario snapshot |
| `POST` | `/v1/runs/:id/pause` | Pause lifecycle advancement |
| `POST` | `/v1/runs/:id/resume` | Resume lifecycle advancement |
| `POST` | `/v1/runs/:id/stop` | Stop a run |
| `GET` | `/v1/spacecraft?run_id=...` | List the modeled fleet |
| `GET` | `/v1/ground-stations?run_id=...` | List simulated sites and antenna capacity |
| `POST` | `/v1/contact-opportunities/search` | Generate deterministic synthetic windows |
| `POST` | `/v1/contact-reservations` | Reserve an opportunity |
| `GET` | `/v1/contact-reservations/:id` | Read current provider lifecycle state |
| `POST` | `/v1/contact-reservations/:id/cancel` | Cancel provider capacity |
| `GET` | `/v1/events?cursor=...` | Consume the ordered provider event feed |

Reservation lifecycle is:

```text
pending -> scheduled -> acquiring -> active -> completed
```

Terminal alternatives are `rejected`, `canceled`, `failed`, and
`terminated_early`.

## Scenario model

The default scenario models 500 spacecraft and three ten-antenna stations.
Visibility is synthetic and explicitly marked as such. Windows are repeatable from
the run seed, spacecraft identity, pass cadence, duration, and bounded jitter.
Changing the run speed compresses future pass cadence and duration into wall time.

Fault profiles support:

- scheduling rejection and complete provider outage;
- acquisition failure and early termination;
- packet loss applied before the network send buffer;
- network latency and deterministic jitter.

Scenario and run definitions, reservations, and events are stored in DETS and
survive restart. High-rate telemetry remains exclusively in Cadence.

## Cadence provider configuration

The existing `ProviderProfile.configuration` may contain a scheduling override:

```json
{
  "mode": "listen",
  "host": "127.0.0.1",
  "port": 4100,
  "framing": {
    "mode": "fixed_size",
    "fixed_message_bytes": 1115
  },
  "fixed_message_bytes": 1115,
  "scheduling": {
    "client": "simulator_http",
    "base_url": "http://127.0.0.1:4101",
    "api_token": "local-simulator-token",
    "delivery_host": "127.0.0.1",
    "run_id": "run-alpha"
  }
}
```

These values are stored on the mission provider profile; there is no global
simulator configuration in Cadence. The control-plane client is selected from the
compile-time provider-client registry. A future plugin model can extend the same
registry and behaviour without changing booking semantics.

`Cadence.Contacts.ProviderBooking` reserves provider capacity first and then
persists the Cadence `ScheduledContact`. A local persistence failure triggers a
best-effort provider cancellation. Contact realization continues through the
existing contact scheduler and TCP provider runtime.

Telemetry definitions remain simulator-owned. Cadence sends the advertised
delivery host, port, and frame size during reservation; it does not send simulator
catalog paths or generator settings.

## Shared CCSDS library

`cadence` and `cadence_simulator` both depend on the leaf application
`cadence_ccsds`. The shared app owns the `Cadence.CCSDS.*` codecs, segmentation,
reassembly, and COP-1 primitives. The simulator has no production dependency on
Cadence core; Cadence is present only in the simulator test environment for
end-to-end integration coverage.
