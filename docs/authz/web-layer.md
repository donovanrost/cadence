# Authorization inventory: the web layer, sockets and client gating

Part of the authorization inventory (`docs/authz.md`, #722 criterion 1). Tree: `develop` at e7584c72d. Line numbers were read from that tree when this was written; re-grep before acting on one. The summary, the proposed action catalog and the findings are in `docs/authz.md`.

Paths: controllers are under apps/cadence_web/lib/cadence_web/controllers/ (`c/` = controllers/console/); plugs/channels/live under apps/cadence_web/lib/cadence_web/; `domain` paths such as control/alarms.ex are under apps/cadence/lib/cadence/.

## Legend

- Principals: **U** = a person using the browser session cookie (CSRF `x-csrf-token` on unsafe methods). **S** = service identity using `Authorization: Bearer`; a bearer request reaches ONLY the {controller, action} pairs in `ServiceAccess @allowed` (section 2.4) and is refused with 403 `service_not_allowed` before any other plug or action runs, on every other route. "U org admin" = organization_admin membership role, or platform admin while in admin mode.
- Route prefixes: **A** = /api/v1, **M** = /api/v1/missions/:mission_id, **O** = /api/v1/organizations/:organization_id.
- Bare file names: `policy.ex` = apps/cadence/lib/cadence/auth/policy.ex; `access.ex`, `service_access.ex` = cadence_web/console/; `mission_scope.ex`, `organization_scope.ex`, `api_session.ex`, `auth_api_session.ex` = cadence_web/console/plugs/; `router.ex` = cadence_web/router.ex.
- Mission routes all sit behind `MissionScope` = `Policy :operate_mission` (any active member of the mission's organization; a mission-bound service). A row that says "NO CHECK in the controller (relies on plug MissionScope ...)" has no other authorization; every other mission row adds the named check on top of it.
- Flags: `per-row` list read that computes a per-item flag; `service-optin` listed in ServiceAccess; `not-server-side` client-only gating (or client weaker/stricter than the server); `no-check` nothing server-side beyond the scope plug; `dup xN` N routes/actions share the check in the row (router lines and controller lines are listed in the same order).
- Since this inventory was taken, #1075, #1171, #1172 and #1174 deleted the LiveView pages, the frontend-release API and its artifact route, and the application-host bridge with its `/host` endpoint; their 8 rows are removed, and the counts below are as written at e7584c72d.
- Counts: 197 rows (14 in section 1, 146 in section 2, 12 in section 3, 25 in section 4); the router has 350 route entries across 340 controller actions.

## Notes (surprises)

1. **Commanding reads are plug-only; writes are fresh-checked.** Group list/show/targets/events/preflight/verifier-series, `endpoints`, `policies`, POST `preflight`, command request history and the command catalog rely on `MissionScope` alone (the readers take `org, mission` ids). `Cadence.Reads.CommandReadAccess` (reads/command_read_access.ex) is a complete operator check referenced nowhere. Siblings differ: encoding and brief (c/command_encoding_controller.ex:14,34) and drafts go through `ReviewAccess` (reloads user and membership from the DB), history does not. `GroupAbort` has its own `authorize` (no fresh user reload, `:operate_mission`) distinct from `ReviewAccess` used by create/decision/notes/release. All three reduce to Policy `:operate_mission` today (todo(authz) comments), so request, approve and abort are the same capability for any member.
2. **One refusal, many shapes.** MissionScope: 404 `mission_not_found` (also for a non-member of a real mission); ReviewAccess / GroupAbort `{:error,:unavailable}` -> 403 `forbidden` (`command_group_problems.ex:23`); Alarms `:forbidden` -> 403; attention `contact_start`/`ingress_backpressure` 403 with custom wording (attention_controller.ex:53-54,201); provider change 403 custom body (provider_change_controller.ex:73); service identity 403 hand-built (service_identity_controller.ex:54); dashboard library 403 hand-built (dashboard_library_controller.ex:40); `AdminController` maps admin-mode loss to 403 `admin_mode_required` but `:forbidden`/`:scope_mismatch` to 404 `not_found` (admin_controller.ex:91,107); `CatalogController#reimport` maps forbidden to 403 but every other error to 404 `artifact_not_found`; bearer on an unknown route 403 `service_not_allowed` where a person gets 404; the application-host bridge uses its own `cadence.application-host-problem.v1` JSON and answers a signed-out caller with a 302 redirect (RequireAuthenticatedScope runs before the JSON 401 plug) while every other JSON API answers 401.
3. **Sibling routes with different checks.** SourceEndpoint READS need `:manage_mission` (c/source_endpoint_controller.ex:18,40) while all other setup reads are plug-only; ElementSet reads plug-only, writes `:manage_mission`; `TransportProviderOptions#show` (a read) requires `config.stage`, sibling config reads need `:read`; `DashboardSharingController#show` needs `:author_dashboards` while `DashboardSettingsController#activity` needs only operate; requirement templates need `:manage_mission` while requirements need `:operate_mission` yet one client token (`planning.edit`) gates both; data-source writes need `:operate_mission` AND `:read_organization` (org admin) while the advertised `data_sources.manage` is operate-only; `PassController#release` is org-admin (booker excepted) while `PassContactController#cancel/finish` are any operator; `ContactRuntimeController#runtime` and `#path_runtime` share `:manage_mission` but only `path_runtime` is service-optin; `CatalogController` opts in index/import_run/artifact/download/apids but not rollout/systems/revision_spacecraft; org-level `configuration` and `pass_review` settings sections need only `:manage_settings` (= any active member at organization scope, policy.ex:71-84).
4. **Mission-scoped service reach (ServiceAccess).** 12 actions (8 table rows in 2.4): catalog reads including `download` (raw source-file bytes) and `artifact`, `CatalogImport#create` (a service may import a catalog as itself; approval stays person-only via `:human_mission_model_approver_required`, policy.ex:152), mission show, spacecraft directory/names/detail, and `ContactRuntime#path_runtime`, which additionally needs `:manage_mission` (a service holding `mission_admin` or `organization_admin`, policy.ex:298-313). Everything else (commanding, alarms, planning, config, dashboards, admin, session) is refused before the action. An organization-level service identity (no mission) cannot pass `MissionScope` at all, and `:operate_organization` always refuses services, so org-level services reach nothing. `ContactPlanController#may_execute` returns `:ok` for any service actor (contact_plan_controller.ex:233) and the `:manage_mission` atom does not pin a mission for an `organization_admin` service (policy.ex:298): both are safe only because ServiceAccess excludes these actions and MissionScope pins the mission first.
5. **Sockets never re-authorize identity after join.** Joins call `Access.authorize_mission` once; no handle_in/handle_info re-reads membership. `disconnect` is broadcast only from password change, revoke-others, revoke-one and sign-out (account_controller.ex:16,45,53,57; session_controller.ex:32), not on removal from the organization, role change, user deactivation or admin-mode expiry. `admin_mode?` is captured in `console_credentials` at connect (console_socket.ex:25) and reused by every later join, so a socket opened in admin mode keeps platform-admin joins after the hour ends. `command_group` pushes recompute with ids only (no ReviewAccess); `dashboard` view:set re-runs `:operate_mission` but against the frozen join-time scope struct. Per-spacecraft joins authorize once per join (500 spacecraft = 500 full `authorize_mission` calls, each a DB session lookup + membership + mission fetch); the mission channel's fleet push is the intended single-subscription path.
6. **Broad reads reachable by any member.** `PeopleController#index` (any active member) returns, for every member, email, role and the evaluated capability list, plus the organization's pending invitations (with their addresses) (administration/organization_people.ex:216-230,241-255; check is only :operate_organization at :30; the client shows People to org admins only); `OrganizationController#missions` returns the organization's whole mission list; `ProviderAccountController#schema` any member. Platform admins in admin mode operate any mission by id without membership (todo(authz) console/access.ex:130, #90 relies on it).
7. **Legacy LiveView host pages** (`/missions/:mission_id/ops/*`) authorize the mission against the session's current organization with `Missions.fetch_mission` only (live/mission_auth.ex:6); `:operate_mission` is applied later by individual reads. The CLAUDE.md says these are being deleted.
8. **Machine surface.** The frontend-release publisher uses one global bearer digest checked in both the endpoint and the router (constant-time compare), no per-publisher identity authentication and no rate limit; artifact GETs are public by design. Sign-in throttling (`AttemptLimit`) is in node memory only (a restart or a second node forgets it).
9. **Per-request cost (500-spacecraft floor).** `GET /session` loops every membership and, for each, `Missions.list_missions` plus three per-mission Policy loops (command, abort, dashboard author); `PeopleController#index` evaluates a Scope per member. Neither grows with spacecraft, but both grow with missions/members on every console load.
10. **Not re-traced here:** `ActivationRequestController#resume` and a few ops-console action internals (named from their Policy call sites only); ServiceAccessTest and per-controller tests were not read.
