# Authorization inventory: the policy core and the access modules

Part of the authorization inventory (`docs/authz.md`, #722 criterion 1). Tree: `develop` at e7584c72d. Line numbers were read from that tree when this was written; re-grep before acting on one. The summary, the proposed action catalog and the findings are in `docs/authz.md`.

Legend. Principals: U = user (human, actor_kind :user); SVC = service identity (actor_kind :service; org-scoped or mission-scoped via `service_identity.mission_id`); PA = platform admin, which only holds the `:platform_admin` capability while admin mode is on (`Scope.user_scope`, apps/cadence/lib/cadence/auth/scope.ex:99-103, 122-126); OA = organization admin (membership role `:organization_admin` gives capability `:organization_admin`, organization_membership.ex:86). A user NEVER holds `:mission_admin` (Scope.user_scope sets mission_id nil and only unions platform_admin + organization_admin), so every "mission admin" rule is reachable only by a mission-scoped service (or OA/PA).
Error atoms: `:forbidden`, `:scope_mismatch`, `:authenticated_user_required` (Policy); see Notes for the others.
Files: P = apps/cadence/lib/cadence/auth/policy.ex.

## Notes

- **Org-level actions are all one rule.** Every action routed through `authorize_organization_capability/4` is the same check (person only, then PA, then org match, then `:organization_admin`): `:read_organization`, `:manage_missions`, `:manage_organization_members`, `:create_missions`, `:manage_provider_accounts`, `:approve_provider_changes`, `:approve_mission_model`, `:approve_contact_plans`, `:manage_fleet_planning_policy`, `:approve_fleet_planning_policy`, `:manage_automation_grants`, `:manage_service_identities`. Names carry no information about who may do it (`read_organization` and `manage_missions` both mean "organization admin").
- **Different error atoms for the same refusal ("a service may not do this"):** `:authenticated_user_required` (most), `:human_mission_model_approver_required` (`:approve_mission_model`, P:152), `:human_activation_approver_required` (`:approve_activation`, P:268). Org mismatch is `:scope_mismatch`, a missing capability or inactive membership is `:forbidden`. Wrapper modules collapse them differently: `ReviewAccess`, `CommandReadAccess`, `Administration.Access` to `:unavailable`; `Configuration.Access` to `:forbidden`/`:mission_not_found`; `Console.Access` and `MissionScope` to 404 `mission_not_found`; `OrganizationScope` to 404 `organization_not_found`; `ActivationPolicy` to `:approval_policy_change_requires_organization_admin` / `...mission_admin`.
- **Users are never mission admins.** `Scope.user_scope` sets `mission_id: nil` and capabilities only `platform_admin` + `organization_admin`. So `:manage_mission` for a user means org admin or platform admin, and `ActivationPolicy`'s "mission admin may tighten" rule and `ApprovalSettingAccess`'s mission-admin branch are reachable only by a mission-scoped service (which `SettingsAccess` refuses) or an org admin. The doc/UX story of a "mission admin" person has no implementation.
- **Mission-scoped service rules.** `:operate_mission` pins a service to its exact org + mission + `:active` lifecycle (P:430-455); a service with no mission_id (org-scoped) gets `:forbidden` from `:operate_mission` (no clause lets an org-scoped service operate a mission). `:manage_mission` is looser: a service holding `:organization_admin` is allowed for ANY mission of its org even if it is mission-scoped, and lifecycle_state and mission-in-org are not checked. `:request_activation` uses `:manage_mission` for services and `:operate_mission` for users. `ServiceAccess` limits what a token may reach to 12 controller actions regardless of Policy.
- **`:manage_mission` for PA returns `:ok` without checking the org or that the mission belongs to it** (P:304); every caller must fetch the mission by org id afterward (ControlPlaneAccess does; not all callers were audited here).
- **Platform admin reach.** In admin mode, `:operate_mission` and `:operate_organization` pass for any org (membership check skipped); the only extra check is mission-in-org. `Console.Access` marks this todo(authz) (access.ex:129). `ReviewAccess` allows PA with no membership (`membership/2` returns `{:ok, nil}`).
- **Defined but never called:** `:read_legacy_application` (only in tests). `ControlPlaneAccess.authorize_mission/3` and `authorize_spacecraft/4` have no callers. `Policy.service_allowed_organization_actions/0` has no non-test callers either (empty list).
- **Called but no clause:** none found for literal atoms. There is no catch-all `authorize/3`, so an unknown atom raises `FunctionClauseError`; dynamic call sites (schedule_commands.ex:37, schedule_operations.ex:367, single_bookings.ex:268 pass `:operate_mission | :manage_missions`; provider_delivery_credentials.ex:390 passes the 3 credential atoms; grant_separation.ex:205 passes `:approve_contact_plans | :operate_mission`; settings_access.ex:10 passes read/manage_settings; configuration/access.ex:92 passes operate/request/approve/manage_mission) were checked and all have clauses. `:"provider_delivery_credential.downgrade"` is called from apps/cadence/lib/cadence/management/transports.ex:90.
- **Capability list is partly hand-written.** `Console.Capabilities.organization/1` (capabilities.ex:21-33) mixes raw Scope capabilities (`organization_admin`, `platform_admin`) with names derived from Policy (`command.request`, `command.approve`, `command.abort`, `org.invite`, `org.manage_members`, `dashboard.author`). The derived names loop `Policy.authorize` over every mission of the org once per organization per session load, and three loops again per member in the People directory (per-row, grows with fleet size: relevant for the per-request-cost rule). `command.request` and `command.approve` are always granted together (same rule). `planning.edit`/`planning.approve` (PlanningPolicy.permissions) are derived from Policy but are not in `Capabilities.organization`.
- **Self-approval / separation is NOT in the Policy module.** `Policy :approve_activation`, `:approve_contact_plans`, `:approve_mission_model`, `:approve_provider_changes` only decide who may be an approver; the self/two-person rules live in `Governance.Accountability.separate/4` and each kind's own module (Configuration.Submission `same_actor?`, ContactPlanApprovals, GrantSeparation, MissionModels.RevisionDecisions, Commanding approval_decisions). `ActivationPolicy.evidence` ("independent" => `separation_of_duties: true`, one human approval; "direct" => none) is the switch they read. `CommandPolicy.policies/0` lists `:no_self_approval` as data only.
- **`:manage_settings` is not a management right.** Any active member of the org (or PA) passes `Policy :manage_settings` (it delegates to operate_organization/operate_mission); the sections' own rules (ActivationPolicy direction rules; configuration/pass-review sections) add anything stricter. Check callers: management/configuration_settings_section.ex:30, pass_review_settings_section.ex:19, settings.ex:27 only use `SettingsAccess` (any member can change those sections).
- **Refusal collapsing hides causes.** `Configuration.Access` turns every Policy error (including `:scope_mismatch`, `:human_activation_approver_required`) into `:forbidden`; `ReviewAccess`/`CommandReadAccess`/`Administration.Access` into `:unavailable`.
- **Live-view guards that bypass Policy:** `OrganizationAuth :require_organization_admin` (hand-written capability test) and `MissionAuth :load_mission` (no `:operate_mission`). LiveView is being deleted per CLAUDE.md.
- **Hot-path caching:** `mission_in_organization/2` caches confirmed (org, mission) pairs in ETS forever (a mission never changes org); a refused pair is re-queried every time.
- **Fresh re-reads:** `ReviewAccess.authorize/2` and `Administration.Access.authorize/1` re-fetch the user (and membership) per call instead of trusting the scope loaded for the request.
