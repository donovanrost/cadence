# Authorization inventory: where the domain layer enforces

Part of the authorization inventory (`docs/authz.md`, #722 criterion 1). Tree: `develop` at e7584c72d. Line numbers were read from that tree when this was written; re-grep before acting on one. The summary, the proposed action catalog and the findings are in `docs/authz.md`.

Paths are relative to `apps/cadence/lib/cadence/` unless they start with `apps/`. Tree: branch based on origin/develop at e7584c72d. Read-only pass.

Legend: `user` = person (Scope actor_kind :user; platform admin only counts while in admin mode); `service` = service identity (actor_kind :service, mission pinned). `op_mission` = Policy `:operate_mission` (user: active org member or platform admin + mission belongs to org; service: its own mission, active identity). `manage_mission` = Policy `:manage_mission` (platform_admin, or organization_admin of the same org, or `mission_admin` capability pinned to this mission; does NOT check the mission belongs to the org). Org-level actions (`:manage_missions`, `:create_missions`, `:read_organization`, `:manage_provider_accounts`, `:approve_provider_changes`, `:approve_mission_model`, `:approve_contact_plans`, `:manage/approve_fleet_planning_policy`, `:manage_automation_grants`, `:manage_service_identities`, `:manage_organization_members`) = person with `organization_admin` (or platform_admin), services refused first.

- Row count above is the table body; every one of the 43 `todo(authz)` hits from `git grep -n "todo(authz)" -- apps` appears (policy.ex:117, :210, :413; data_sources.ex:876; expired_group_attention.ex:149; archive_quarantine:236; contact_settlement:189; contact_start:152; ingress_backpressure:112; job_outcome_unknown:222; scid_mismatch:154; single_bookings:33; activation_requests.ex:8; resume.ex:32; command_brief:24; command_encoding_preview:20; command_drafts:50; group_abort:160; group_decision:72; group_notes:15; group_release:58; group_submission:33; dashboards/capabilities:21; activation_policy:142; approval_setting_access:66; management/commanding.ex:21; review_access.ex:62; revision_decisions.ex:296; change_set_items.ex:19; and the 13 web ones plus the test line).
- User scopes always have `mission_id: nil` (`Scope.user_scope`). So every `scope.mission_id in [nil, mission]` check is meaningful only for service scopes (which `Policy.authorize_service_mission` already pins). `:operate_mission` for a user never looks at `scope.mission_id`; the repeated hand-written pin checks are redundant for people and absent in other modules (alarms, station availability, pass review, contact planning writes).
- `:operate_mission` is the effective rule for roughly 90% of these call sites: any active org member operates every mission of the org. Org-level actions need `organization_admin`. There is no per-mission membership, per-spacecraft, per-command or per-provider rule anywhere in the domain layer.
- `:manage_mission` does not verify the mission belongs to the organization (only `:operate_mission` calls `mission_in_organization`); an org admin passes for any mission id string, so tenant safety there depends on every domain query filtering by `organization_id`. `:platform_admin` short-circuits before the org check in both `manage_mission` and org-level actions (admin mode only: `Scope.new` strips `:platform_admin` outside it).
- `mission_admin` capability is never held by a person (user capabilities are `platform_admin` plus the membership role's `organization_admin`); only service identities carry it. The "mission admin may tighten" branch of `ActivationPolicy.save` and `ApprovalSettingAccess.mission_admin?` is therefore reachable only by org admins, while `SettingsAccess` requires a user, so the mission-admin path is effectively dead.
- Settings: `SettingsAccess` maps `:manage_settings` with no mission to `:operate_organization`, i.e. any active member can edit org-level pass-review and configuration settings; only the governance (approval) section adds an admin rule.
- Data sources: the todo says "any mission operator", but `DataSources.authorize` also requires `:read_organization` (org admin) for every action, reads included.
- (Corrected in verification.) Fleet planning policy approve and reject DO refuse the policy's author: `not_author/2` in `decide_transaction`, fleet_planning_policies.ex:354-365, unconditional, comparing `created_by` with the actor's `user_id`. The kind with no requester-vs-approver check at all is **provider change approval**.
- Self-approval rules by area: command groups unconditional (requester); activations unconditional (requester) plus conditional spacecraft-config author rule; change-set review unconditional; contact plans, automation grants and mission models conditional on `separation_of_duties`. `can_decide` flags in activation rows compare raw `requester_actor_id != viewer`, which differs from Accountability's service-requester expansion used when enforcing.
- Ordering: `Control.Contacts.execute_approved_plan` writes execution items (`accept_approved_plan`) before `ContactPlanExecutions.execute` authorizes. `Reads.MissionModelApprovals.approve` reads `ModelApprovalGate.running?` before authorizing. `Control.Scheduling.edit_plan` reads the plan before `version_plan` authorizes.
- `Policy.authorize(:request_activation)` receives `change_class` in several callers but the policy ignores it; every activation change class has the same permission.
- Overloaded `Scope.t() | binary()` provider functions (`validate_provider`, `sync_provider`, `persist_provider`, `archive_provider`) have a binary-organization clause that skips authorization; callers must be internal.
- Several read endpoints authorize with a write permission: activation list uses `:request_activation`; delivery credential `show` uses `:issue`; provider account reads need org admin (`:read_organization`).
- Per-request cost: People directory evaluates `Commanding.capabilities` + `GroupAbort.capabilities` per member, each listing all org missions; `Dashboards.Capabilities` and the session do the same per request. Fleet planning authorizes once per run, once per 250-requirement batch and once per phase in production (the per-requirement path runs only through test seams). The grant ledger's extra reads apply only to proposed grants (2 settings reads each) and suspended grants (1); the replaced-proposer query only to replacing proposals under 'independent' (verified).
- `ReviewAccess.authorize` re-reads user, membership and mission on every call, so each commanding action costs three queries before its own work; it also rebuilds a scope, discarding the caller's `capabilities` (platform admin mode is carried only via `admin_mode?`).
